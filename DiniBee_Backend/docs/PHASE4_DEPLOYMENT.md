# Phase 4 upgrade and database notes

Keep the existing PostgreSQL database and configuration keys. Do not edit applied migrations, recreate authentication tables or regenerate keys. Phase 4 adds V6–V8; V1–V5 remain byte-for-byte unchanged. There are no new Maven dependencies or environment variables.

| Migration | Changes |
|---|---|
| V6 | restaurant_tables, table_allocations, btree_gist, composite ownership FK, partial uniqueness and overlap exclusion |
| V7 | menu_categories, menu_items, menu_variants, menu_addons, prices/checks, composite category ownership FK and current-name indexes |
| V8 | TABLE_MANAGE and MENU_MANAGE permissions for OWNER and SUPER_ADMIN |

`btree_gist` is required for UUID equality in the multicolumn GiST exclusion constraint. PostgreSQL supplies it as a trusted extension; installation requires suitable database privileges and extension availability. The existing Compose PostgreSQL 17 image is the intended local target. On a managed database, enable the extension for the application database through its supported administration path before migration if the migration role cannot install it. Do not remove the exclusion constraint to make a migration pass. [PostgreSQL 17 btree_gist](https://www.postgresql.org/docs/17/btree-gist.html)

V6 executes `CREATE EXTENSION IF NOT EXISTS btree_gist`. The protected range is generated by PostgreSQL from starts_at and ends_at; JPA intentionally does not map that extra column. Hibernate continues to validate entity mappings. Dining end and protected end are separate timestamps so grace remains explicit. Composite foreign keys ensure allocations use a table from the same restaurant and menu items use a category from the same restaurant.

Starting from Phases 1–2: first follow [PHASE3_DEPLOYMENT.md](PHASE3_DEPLOYMENT.md) to add the independent settlement key without replacing existing secrets. Starting from Phase 3: keep the existing `.env`; normal startup applies V6–V8. New installations use the existing init-env script and all eight migrations.

Run in the project directory:

```bash
mvn clean test
mvn clean package
mvn clean verify -Pintegration
```

Docker must be running for Testcontainers. These build/database gates could not run in the authoring environment; the source is not a verified release. Resolve failures in a development/CI environment before deployment or Phase 5. No production database was migrated, application deployed, or frontend connected during this work.

After the verified build, start the existing Compose/native workflow and check:

1. Existing auth/profile and onboarding flows remain usable.
2. An owner can create a table/category/item in a draft and after approval; another owner cannot access those resources.
3. Approved active RESTAURANT service with reservations/hours and a fitting table yields slots; disabling the service removes availability.
4. Availability reads create no allocations. Booking creation remains absent until Phase 6.
5. Review the Testcontainers concurrency and SQL exclusion tests before any booking writer is exposed.
